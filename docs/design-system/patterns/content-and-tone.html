Pattern

Content and tone

Invitely writes like a well-organised friend: plain and exact with organisers, warm with guests, and never makes either of them guess what happens next.

Overview

This pattern applies the rules in the content foundation to the strings that appear across the mocks, so the same thing is always said the same way. It covers every component's Content section and the copy in forms, notifications and empty and error states.

AudienceVoiceExample from the mocks
OrganisersDirect and exact: counts, dates, what happens next“84 people will receive the invitation. Reminders follow automatically.”
GuestsWarm, first and second person, the host's name“Hi Jonah, will you join us?”, “We’ll tell Maya.”
Both, when something failsCalm: what didn’t happen, that nothing was lost, what to do“Your answer is still on this page. Check your connection and try again.”

“Invitely” is a placeholder product name (mocks README, question 1); it appears only in the shell, titles and the “Sent with Invitely” footer, so it can be replaced in one pass.

When to use which

WritingRuleExample
ButtonsVerb + object in sentence case; the object can drop when the context gives it“Schedule invitations”, “Add guest”, “Remove 2 guests”, “Send my RSVP”
Headings and titlesSentence case, no full stop“Invite window”, “Danger zone”, “Invites are open”
Body and help textFull sentences with full stops; one idea each“Shown on the public page and in every email.”
LabelsNouns; “(optional)” on optional fields only“Event name”, “Venue (optional)”
Status badgesOne or two words, the state“Attending”, “Waiting”, “Invites open”, “Opens 26 Oct”
Destructive confirmationsA question with the object; the confirm repeats the verb“Remove 2 guests?” → “Remove 2 guests”

Formulas

  1. Error What went wrong + what is safe + what to do. “Links weren’t reset. Nothing changed. Try again.”
  2. Field error The fix, as an instruction. “Enter an email like name@example.com.”
  3. Empty What is true + how to start. “No invitees yet. Import a CSV from a spreadsheet, or add people one at a time.”
  4. Success The thing + the result + the next step. “81 guests imported. Nothing was sent yet; schedule the invitation when you are ready.”
  5. Confirmation The question + the loss + the reassurance. “Reset invitation links? Use this only if a link has leaked.”

Responsive behaviour

  • Write for 360px first: button labels fit on one line; page titles may wrap (they balance), badges never do.
  • Long event names truncate only in lists and tables, with the full name in the link; titles and headings show it whole.
  • Do not shorten copy for phones with abbreviations; cut words instead (“Add guest”, not “Add gst”).
  • Dates keep their format at every width; the time zone note moves under the date on narrow screens.

Accessibility

  • Link and button text makes sense alone: “View public page”, “Remove Jonah Adeyemi”, never “Click here” (SC 2.4.4).
  • Icon-only controls name the action and the object in aria-label.
  • Visually hidden text completes what the layout implies: “Select Jonah Adeyemi”, “Loading guests”.
  • Status in words, not colour: “Attending”, “· unread”, “Invites closed” (SC 1.4.1).
  • Error text names the field and the fix (SC 3.3.1, 3.3.3); the summary and the field say the same sentence (L2-087).
  • Plain language: short sentences, common words, no jargon such as “RSVP token” or “payload” on guest pages.

Content

  • Sentence case everywhere, including buttons, tabs, badges (set in caps by CSS, written in sentence case) and page titles.
  • Curly apostrophes and quotes (’ “ ”), the ellipsis character (…), en dashes for ranges.
  • Contractions are fine (“can’t”, “we’ll”); exclamation marks only in guest celebrations (“Thanks, Jonah! See you on Saturday.”).
  • Say “invitees” for people on the list, “guests” for the people coming (including plus-ones), “organiser” for Priya.
  • UK spelling (organiser, recognise), matching the mocks.
