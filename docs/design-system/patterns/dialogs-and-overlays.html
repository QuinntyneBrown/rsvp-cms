Pattern

Dialogs and overlays

A dialog interrupts. Use one only when the person must decide or enter a little information before going on, and give them a safe way out.

WCAG 2.2 AA

Overview

The mocks have nine dialogs: delete event (typed confirmation), add or edit guest, remove guests, schedule invitations, email preview, add a CMS block, discard unpublished changes, reset invitation links and decline an RSVP. They share one dialog component: header with title and one-line description, body, a footer with the actions, a close button, a backdrop and an inert page behind.

The overlays in the system are the dialog, the menu (account menu) and the tooltip. Drawer and popover are not part of the system: no mock needs a side panel or a non-modal floating panel. If one is needed later, it starts as a mock and a design-system page.

  2. Contain Tab cycles inside; the page behind is inert and aria-hidden (L2-086).
  3. Act the confirm button goes busy; the dialog waits for the request.

States

  • Busy: the confirm button shows aria-busy. While the request is in progress Esc does not close the dialog (L2-086); it closes on success, or shows the failure.
  • Invalid: form dialogs use the same linked error summary as pages (see forms).
  • Failed: a danger alert at the top of the body says nothing changed and offers Try again; the dialog stays open.
  • Success: most dialogs close and a toast confirms. Only when the result needs reading (when invitations will go out) does the dialog change to a success state with Done.
  • Stacking: never open a dialog from a dialog. Discard changes is opened from the CMS page, not from the block picker.

Responsive behaviour

  • From 36rem the dialog is centred with 24px around it, at most --layout-dialog-max (35rem, 560px) wide; the small size stays 24rem (L2-083).
  • There is no larger size: the email preview and block picker, which the mocks drew at 48rem, are capped at 35rem; the picker's cards fall into one column.
  • Below 36rem the dialog fills the screen: full height, no radius, footer sticky at the bottom so the actions stay above the keyboard (L2-083).
  • The body scrolls; the header with the close button and the footer do not, so Close is always visible.
  • Under (pointer: coarse) the close button and footer buttons have 44×44px hit areas (L2-084).
  • Footer buttons wrap; the primary or danger action stays last.

Accessibility

  • role="dialog", aria-modal="true", aria-labelledby the title and aria-describedby the description (APG Dialog (Modal) pattern).
  • The page behind is inert; focus cannot reach it and screen readers do not read it.
  • Every dialog has a labelled close button (“Close”) as well as Cancel.
  • Destructive dialogs name the loss in text, not only with the red button (SC 1.4.1, 3.3.4).
  • When the dialog closes, focus returns to the control that opened it; after a delete, to the list's heading (L2-086).
  • The panel enters over --duration-base; under reduced motion it appears without scaling or sliding (L2-089).

Keyboard

KeyAction
Tab / Shift+TabCycles through the dialog's controls only.
EscCloses, like Cancel, unless a request is in progress (L2-086).
EnterSubmits a form dialog from a text field; it never confirms a destructive dialog by default.

Content

  • Titles ask the question with the object: “Remove 2 guests?”, “Delete “Maya’s 30th birthday”?”, “Reset invitation links?”.
  • The description is one short line: what is safe, or what cannot be undone.
  • The confirm label repeats the verb and object of the title: “Remove 2 guests”, “Delete event”, “Reset links”. Never “Yes” or “OK”.
  • The safe action says what it keeps when that helps: “Keep editing”, “Keep my reply”; otherwise “Cancel”.
  • Use one verb for one action everywhere: the settings row, its button, the dialog title and the confirm button all say “Reset”.
