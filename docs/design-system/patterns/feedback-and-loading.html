Pattern

Feedback and loading

Feedback appears where the person is looking and says what happened. Loading shows the shape of what is coming, not a blank page.

WCAG 2.2 AA

Overview

Every action gets an answer: a busy button while it runs, then a confirmation or an error in the place that matches its scope. Every page gets a loading state that keeps its header and lays out skeletons where the data will be. Components: toast, alert, inline message, progress, spinner, skeleton.

When to use which

  1. Act the pressed control goes busy at once (within 100 ms).
  2. Wait skeleton, spinner or progress, matched to the wait.
  3. Answer confirmation where the result is, or an error beside the cause.
  4. Recover every error offers the next step: Try again, Undo, Review.

States

  • Loading keeps the page header and tabs real; only data regions become skeletons, in a container with aria-busy="true" and a visually hidden label (“Loading guests”).
  • Busy controls keep their label and size; no other control on the page is disabled.
  • Partial failure replaces only what failed; never blank a page because one request failed.
  • Error on a whole region becomes an error state with Try again.
  • Success is quiet: a status line or a toast, never a dialog, except when the result needs reading (Invitations scheduled for Mon 19 Oct at 9:00 am).

Responsive behaviour

  • Toasts sit bottom-right at 24rem wide from 36rem; below that they span the width above the safe area.
  • Skeleton grids use the same grid classes as the loaded page, so nothing jumps when data arrives.
  • Inline status wraps under the actions at 360px; it stays next to the button it describes in reading order.
  • Banners span the content width and wrap their actions.

Accessibility

  • Status messages are announced without moving focus (SC 4.1.3): toasts and inline status are polite (role="status"); errors are assertive (role="alert") (L2-087).
  • Error toasts are announced from their own assertive region next to the polite one; an alert nested inside a status region can be announced twice or not at all.
  • Busy regions set aria-busy="true" and are labelled; skeleton shapes are aria-hidden by being empty.
  • Progress bars have role="progressbar", a label and aria-valuenow; the count is also written as text.
  • Auto-dismissing toasts last at least 8 seconds and pause on hover and focus; errors never auto-dismiss (SC 2.2.1).
  • Toasts and banners enter over one token, --duration-base; under reduced motion they appear with no slide or fade (L2-089). Shimmer and indeterminate animations stop; spinners slow down instead.
  • Status text in every tone passes 4.5:1 in both themes (L2-085).

Content

  • Confirmations name the thing and the result: “Event details saved”, “81 guests imported”, “RSVP saved”.
  • Errors say what did not happen, that nothing was lost, and what to do: “Couldn’t save your changes. Your edits are still on this page. Check your connection, then try again.”
  • Loading labels name the content: “Loading guests”, never “Please wait”.
  • Progress uses counts the person recognises: “49 of 81 added”.
  • Undo is the only toast action for reversible changes; View or Try again otherwise. One action per toast.
