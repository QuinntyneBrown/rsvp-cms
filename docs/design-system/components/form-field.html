Form field

Every input in Invitely sits in a form field: a visible label above, the control, then help, an error or a counter beneath. One structure, so every form reads and announces the same way.

Overview

The form field is the wrapper, not a control. It holds one text field, textarea or select and the text around it. Groups of checkboxes and radios use <fieldset> and <legend> instead, because one label cannot name several controls; see form layout for fieldsets, rows and the error summary.

  • Label always, above the control.
  • Optional marker “(optional)” inside the label when the field can be left blank. Invitely marks the optional fields, not the required ones, because most fields are required.
  • Help when the purpose or format is not obvious.
  • Error after blur or submit, replacing nothing: help stays visible above it.
  • Success only for a check the server did, such as an invitation code that was found (a system addition; no mock uses it yet).
  • Counter only when there is a limit.

Anatomy

  1. Label.field__label, --text-label (14px medium), --color-fg-default.
  2. Optional marker.optional inside the label, regular weight, --color-fg-subtle.
  3. ControlAny input, select or textarea; --space-1 (4px) below the label.
  4. Help / error / success--text-body-sm, 4px below the control; error and success carry a ⚠ or ✓ glyph so colour is not the only signal.
  5. Counter.field__counter, caption size, right-aligned.

Sizes

The form field has no sizes; it takes the size of its control, and its text sizes are fixed so labels line up across a form.

States

The wrapper’s parts are its states. Interaction states (hover, focus, disabled) belong to the control and are on each control’s page.

Responsive behaviour

  • The label always sits above the control, at every width. Side-by-side labels are not used: they break at 360px and at 200% zoom.
  • Fields fill their column; two short fields share a .form-row only from 48rem.
  • Help and error text wrap freely; nothing in a field truncates.

Theming

The field has no component tokens of its own; it uses --color-fg-default (label), --color-fg-subtle (optional, counter), --color-fg-muted (help), --color-danger-fg (error) and --color-success-fg (success), all checked at 4.5:1 on surfaces in both themes.

Accessibility

Role and pattern

A <div class="field"> with a <label for>; no ARIA role. The relationship is carried by for/id and aria-describedby.

Keyboard

KeyAction
TabGoes straight to the control; label, help and error are not focusable.
Click or tap the labelFocuses the control (a bigger target).

Focus

On submit with errors, focus goes to the error summary; each summary link moves focus to its field, and the field’s error is read with it.

Labelling

  • aria-describedby lists help, then error, then counter, so the reading order matches the visual order.
  • Invalid controls set aria-invalid="true"; the error text names the problem and the fix.
  • Required controls set required; optional ones say “(optional)” in the label, which is part of the accessible name.
  • A success message is in role="status" so it is announced without moving focus.

Motion

Errors and success appear without animation, so nothing shifts while someone reads.

Touch

The label extends the tap target of the control above it.

Content

  • Label: a noun phrase, sentence case, no colon: “Guest’s name”, “Party size”.
  • Optional marker: exactly “(optional)”, lower case, in brackets.
  • Help: one sentence about use or format: “Allergies and anything the kitchen must know.”
  • Error: what to do, in the field’s terms: “Enter the guest’s full name.”, “Choose a later close date.” Never “Invalid input” or “Required”.
  • Success: what was found, by name: “Found your invitation, Jonah.”
