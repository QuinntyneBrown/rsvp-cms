Component · Inputs

Text field

Text fields take one line of typing: an event name, a guest’s email, an invitation code, a date. They always sit inside a form field with a visible label.

WCAG 2.2 AAStatus: stableNative <input>

Overview

Use a text field when the answer is short, free-form and typed: “Event name”, “Full name”, “Email”, “Invitation code”, “Song request”. For more than one line use a textarea; for a fixed list (event type, meal, time zone) use a select or, with five or fewer options that benefit from being seen, a radio group.

  • Always inside a form field: the field supplies the label, help, error and counter; this page covers the control.
  • Use the right type: email on sign-in, account and guest forms; password on sign-in and reset; search in the top bar and above tables; native date and time for event dates, invite windows and send times.
  • Search is the one field whose label is visually hidden: the magnifier and the placeholder (“Search events and guests”) make the purpose plain, and the label still names it for assistive tech.

Anatomy

  1. LabelFrom the form field: --text-label, sentence case, always visible.
  2. Container--control-height-md (40px) tall, 1px --color-border-strong, --radius-md, padding --space-2 × --space-3.
  3. Value / placeholder--text-body (16px, so phones do not zoom). Placeholder in --color-fg-subtle is an example, never the label.
  4. Help textFrom the form field, linked with aria-describedby.

Variants

The control is the same box for every type; the browser supplies the keyboard, autofill and picker. Pick the type for the data, not the look.

Sizes

Medium (40px) is the default everywhere in the mocks. Small (32px) is for dense filter bars and table toolbars; large (48px) is reserved for a single-field page such as the public “Find my invitation” form and is not used by the mocks yet.

.input--sm / default / .input--lg; heights --control-height-sm/md/lg.
HTML
<input class="input input--sm" type="text" value="Small · 32px" aria-label="Small example">
<input class="input" type="text" value="Medium · 40px" aria-label="Medium example">
<input class="input input--lg" type="text" value="Large · 48px" aria-label="Large example">

Both themes

  • Invalid is aria-invalid="true" plus a field error linked by aria-describedby; the border thickens to 2px of --color-danger-solid so it does not rely on colour alone. Set it after blur or submit, never while the person is still typing.
  • Read-only keeps the value readable and focusable on a sunken surface. The new-event form uses it while submitting, so the values stay visible but cannot change mid-request.
  • Disabled removes the field from the tab order. Use it only when the reason is explained next to it, as on the public page before invites open (“Your invitation email arrives that morning”).
  • Required uses the required attribute so screen readers announce it; the label stays clean because Invitely marks the optional fields instead.

Responsive behaviour

  • Fields are full width of their column at every breakpoint; the container, not the field, sets the line length (organiser forms sit in .container--narrow, --layout-container-narrow 42rem; the public RSVP form is capped at --layout-form-max, 45rem, per L2-082).
  • Two short related fields (date and start time, opens and closes) sit side by side in .form-row from 48rem; below that they stack.
  • The top-bar search grows to fill the bar up to 28rem and stays visible at 360px; the menu button and bell sit beside it.
  • Text stays 16px at every size on phones (only .input--sm drops to 14px, and it is not used on phone-first public pages) so iOS does not zoom on focus.
  • Native date and time pickers are used on every platform; they bring their own touch-friendly UI.

Theming

The control reads component tokens --field-bg, --field-border, --field-border-hover and --field-height, which alias --color-bg-surface, --color-border-strong, --color-fg-muted and --control-height-md. Themes change the semantic tokens; a surface that needs a different field look overrides the component tokens.

/* Fields on a sunken well read as raised */
.well .input { --field-bg: var(--color-bg-surface-raised); }

In dark the border lifts to --palette-gray-450 so it keeps 3:1 against both the surface and the raised dialog background; color-scheme: dark makes the native date and time pickers dark too.

Accessibility

Role and pattern

Native <input> with a <label for>. No ARIA role. Search sits in <form role="search"> so it is a landmark. The password Show toggle is a <button aria-pressed> that switches the input's type.

Keyboard

KeyAction
Tab / Shift+TabMoves into and out of the field.
Typing, arrows, Home / EndNative text editing; date and time fields step segments with arrows.
EnterSubmits the surrounding form (search runs the search).
EscClears a type="search" field in most browsers; inside a dialog it closes the dialog.

Focus

Focus draws the shared 2px ring flush with the field (offset 0) and turns the border to --color-focus-ring. On submit with errors, focus moves to the error summary, whose links move focus into the field.

Labelling

Every field has a visible label (L2-087) except search, whose label is .visually-hidden. Help and error ids go in aria-describedby, help first. Fields for the person’s own details set autocomplete (email, name, current-password, new-password) for WCAG 1.3.5; guest emails an organiser types for someone else do not.

Motion

Border colour and the invalid inset shadow transition over --duration-fast; reduced motion makes them instant.

Touch

Under (pointer: coarse) every field, small ones included, is at least 44px tall (--target-comfortable, L2-084); with a fine pointer medium fields are 40px. The label is part of the target because tapping it focuses the field.

Content

  • Labels are short nouns in sentence case: “Event name”, “Full name”, “Email”, “Start time”. No colon, no “Please enter”.
  • Mark the exception: optional fields say “(optional)” in the label; required ones say nothing.
  • Help text says what the value is used for or its format: “Shown on the public page and in every email.”, “At least 12 characters.”
  • Placeholders only show an example or search scope (“Search by name or email”); they disappear on typing, so they never carry instructions.
  • Errors say what to do: “Enter an email like name@example.com.”, “That date has already passed. Pick a date after today.”
