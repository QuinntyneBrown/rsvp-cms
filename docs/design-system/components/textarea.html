Textarea

Textareas take more than a line: dietary needs, a note with a decline, a message for the host, the copy of a CMS block.

WCAG 2.2 AAStatus: stableNative <textarea>

Overview

Use a textarea when the answer may run to a sentence or more and line breaks are allowed. In the mocks: “Dietary needs” and “Message for Maya” on the RSVP form, the optional message in the decline dialog, and the supporting line of the CMS hero block. For a name, email or code use a text field, even if the value might be long.

  • Always inside a form field, with a visible label.
  • Set rows to the length you expect: 2 for a short note, 3 for a message. The height tells people how much to write.
  • Add a counter only when there is a real limit (the RSVP message is 280 characters).

Anatomy

  1. LabelFrom the form field.
  2. ContainerSame border, radius and padding as the text field; minimum height two control heights (80px), or rows if taller.
  3. Resize handleVertical only (resize: vertical) so the layout never widens.
  4. Counter (optional).field__counter, right-aligned caption, linked with aria-describedby.

Sizes

There is one size: the type and padding match the medium text field. Height comes from rows; the minimum is 80px so even a one-row textarea reads as multi-line.

rows sets the starting height; people can drag it taller.
HTML
<textarea class="textarea" rows="2" aria-label="Two rows example">rows="2" · short notes</textarea>
<textarea class="textarea" rows="3" aria-label="Three rows example">rows="3" · messages</textarea>
<textarea class="textarea" rows="6" aria-label="Six rows example">rows="6" · long CMS copy such as the FAQ answer</textarea>

States

Hover and focus are forced with data-state; invalid, disabled and read-only use real attributes. Over the limit, the counter turns danger-coloured and the field is marked invalid on submit, not while typing.

Responsive behaviour

  • Full width of its column at every breakpoint; the form’s container caps the line length.
  • Never placed in a two-column .form-row: multi-line text needs the width.
  • Resize is vertical only, so dragging can never push the page wider than the viewport at 360px.
  • Text stays 16px so phones do not zoom on focus; the on-screen keyboard keeps Enter as a new line.

Theming

Shares the text field’s component tokens: --field-bg, --field-border, --field-border-hover. Override them on a container to re-skin every field in it at once; the textarea needs nothing of its own.

In dark the field keeps the surface colour and the border lifts to --palette-gray-450, so the box stays visible inside raised dialogs such as the decline dialog.

Accessibility

Role and pattern

Native <textarea> with <label for>; no ARIA role.

Keyboard

KeyAction
Tab / Shift+TabMoves into and out of the field. Tab never inserts a tab character.
EnterInserts a new line; it does not submit the form.
Arrows, Home / EndNative text editing.

Focus

The shared ring, flush with the field, plus a focus-coloured border; the same as the text field.

Labelling

The counter is linked with aria-describedby so its limit is read on focus. Updates are not announced on every keystroke; a visually hidden live region announces “20 characters left” once typing pauses and when the limit is passed.

Motion

Border transitions over --duration-fast; auto-grow changes height without animation.

Touch

At least 80px tall and full width, so it exceeds the 44px coarse-pointer target (L2-084); the label also focuses it.

Content

  • Label the topic, not the action: “Dietary needs”, “Message for Maya”, not “Type your message here”.
  • Use help text to set expectations: “Allergies and anything the kitchen must know.”
  • Counters read “42 of 280”; when over, “312 of 280” plus the error “Shorten your message to 280 characters.”
  • Leave the field empty rather than pre-filling filler text guests must delete.
