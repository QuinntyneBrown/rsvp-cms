Inline message

An inline message is one short line attached to a field or a control: how to fill it in, what is wrong with it, or whether the page’s changes are saved.

WCAG 2.2 AAStatus: stable

Overview

Use an inline message for information about one field or one control, placed directly beneath or beside it. Use an alert for a problem with the whole form or region, and a toast for the result of an action elsewhere.

  • Hint (.field__help): how to fill the field in. Always visible, never a placeholder.
  • Error (.field__error): what is wrong and how to fix it, after a failed submit or on blur.
  • Success (.field__success): confirms a value checked by the server, such as an available page address. Rare.
  • Counter (.field__counter): characters used of the limit.
  • Inline status (.inline-status): the save state of a page, next to its actions: “Draft · saved 2 min ago”, “Saved at 10:42 am”.

Anatomy

  1. LabelOwned by the form field.
  2. FieldGets aria-invalid="true" and aria-describedby pointing at the message.
  3. IconA warning glyph drawn by CSS (::before), so the error is not colour alone.
  4. Message--text-body-sm in --color-danger-fg; one sentence saying how to fix it.

Sizes

Inline messages take the small body size of the field they belong to; there is one size.

  • Error timing: errors appear on submit, and for fields already touched, on blur. They clear as soon as the value becomes valid while typing.
  • Inline status moves draft → publishing → saved, or → not saved; it updates in place inside a role="status" span so each change is announced once.

Responsive behaviour

  • Messages wrap under the field at every width; they never truncate.
  • Inline status sits at the start of the page’s action row and wraps above the buttons on phones (the row is a .cluster--between).
  • The counter stays right-aligned under its textarea.

Theming

Hint and counter read --color-fg-muted and --color-fg-subtle; error and success read --color-danger-fg and --color-success-fg. All four are tuned to pass 4.5:1 on surface, raised surface (dialogs) and canvas in both themes, so a message can sit anywhere a field can.

Accessibility

Role and pattern

Field messages are plain text referenced by the control’s aria-describedby; a screen reader reads them after the label. Errors pair with aria-invalid="true" (WCAG 3.3.1). Inline status is a role="status" live region (WCAG 4.1.3).

Keyboard

KeyAction
TabMessages are not focusable; focusing the field reads its message.
Error summary linkMoves focus to the field, which then reads its error.

Focus

Showing an error never moves focus by itself; after a failed submit focus goes to the error summary, not to the first message.

Labelling

Every message has an id and is listed in its field’s aria-describedby (hint first, then error). The counter is described too, but only announced on focus, not on every keystroke.

Motion

Messages appear without animation. The “Publishing…” dot pulses; reduced motion stops the pulse.

Touch

Not interactive; nothing to tap.

Content

  • Errors say how to fix, not what went wrong: “Enter an email like name@example.com.”, “Invites must close after they open. Choose a later close date.”
  • Name the field’s subject in the guest’s words: “Choose a meal for each guest.”
  • Hints give a concrete example: “The code is on your invitation email, like MAYA-7K2Q.”
  • Status names the time: “Saved at 10:42 am”, “Draft · saved 2 min ago”.
  • The same sentence appears in the field error and in the error summary.
