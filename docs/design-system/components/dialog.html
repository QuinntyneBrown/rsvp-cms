Dialog

A dialog takes over the screen for one decision or one short task, then gives control back exactly where it was. Invitely uses nine: delete event, add or edit guest, remove guests, schedule invitations, email preview, add a block, discard changes, reset links and decline an RSVP.

Overview

Use a dialog when the person must decide before continuing (“Delete “Maya’s 30th birthday”?”), or for a task of a few fields that belongs to the page behind it (edit a guest). Use a page for anything longer than one screen or anything people want to link to (new event, guest import); use a toast to report an outcome; use inline content for help.

  • Confirmation: title as a question, consequence in one sentence, the safe action and the action.
  • Destructive: a danger icon, role="alertdialog", a danger confirm button; for irreversible loss of a whole event, a typed confirmation that enables the button.
  • Form: a few fields with an error summary on submit (add or edit guest, schedule invitations).
  • Scrolling: previews and pickers (email preview, add a block) keep the 35rem maximum; the body scrolls while the header with Close and the footer stay put.
  • Below 36rem every dialog fills the screen: full height, no radius, footer sticky at the bottom (L2-083).

Anatomy

  1. Icon (destructive only).dialog__icon--danger: 40px circle, danger tint, aria-hidden.
  2. Heading.dialog__heading holds the title (--text-h3, the accessible name) and the description (the accessible description).
  3. CloseGhost icon button labelled “Close”; same as Cancel.
  4. Body.dialog__body, 16×24px padding; scrolls when tall.
  5. FooterSticky, hairline rule, safe action then the action, right-aligned.
  6. Panel and backdrop--color-bg-surface-raised, --radius-lg (none when full screen), --shadow-4; backdrop --color-bg-backdrop.

  • Ready: the destructive button enables once the confirmation matches; it stays disabled before that, with the help text explaining why.
  • Busy: the action button gets aria-busy="true" (spinner, clicks ignored). Cancel and Close keep their look but are aria-disabled="true" and Esc does nothing until the request ends (L2-086); they stay focusable, so focus is never lost.
  • Failed: a danger alert at the top of the body says nothing changed and how to retry; the dialog stays open with the person's input intact.
  • Invalid (forms): an error summary at the top of the body receives focus and links each field error.
  • In dark the panel is the raised gray-800 surface over a 65% black backdrop, so it reads as above the page without relying on shadow.

Responsive behaviour

  • Below 36rem (--layout-breakpoint-sm): full screen, full height, no radius, footer sticky at the bottom; slides up over --duration-base.
  • From 36rem: centred with 24px around it, at most --layout-dialog-max (35rem) wide, --radius-lg corners, scales in over --duration-base.
  • Maximum height is 100dvh minus 48px; the body scrolls and the footer is sticky, so the actions are always visible (email preview).
  • Footer buttons wrap when they do not fit; the action stays last.
  • The close button stays visible in the header at every size; never put a two-column layout in a dialog.

Theming

The panel reads --color-bg-surface-raised, --color-fg-default, --color-border-default (footer rule), --shadow-4, --radius-lg and the backdrop --color-bg-backdrop. Width is the component token --dialog-width (defaults to --layout-dialog-max, 35rem; --sm 24rem; --lg is capped at 35rem). The icon reads the status tokens (--color-danger-bg, --color-danger-icon).

/* A narrower confirmation for one product area */
.dialog__panel--confirm { --dialog-width: 28rem; }

Accessibility

Role and pattern

APG Dialog (Modal): role="dialog" (or role="alertdialog" for destructive confirmations), aria-modal="true", aria-labelledby on the title and aria-describedby on the description. Everything behind is inert, so screen readers and Tab cannot reach it.

Keyboard

KeyAction
Tab / Shift+TabCycles through the dialog's controls only; focus never leaves the dialog.
EscCloses the dialog, same as Cancel and Close, unless a request is in progress (L2-086).
EnterActivates the focused button; in a form it submits only when focus is in a single-line field.
SpaceActivates the focused button or toggles a checkbox.

Focus

On open, focus moves into the dialog: to the first field in a form (guest name, the delete confirmation field), to the safe action in a confirmation without fields (“Keep editing”, “Cancel”), and to the panel's heading in a read-only preview. On close, focus returns to the control that opened it (“Delete event” in the danger zone). After an invalid submit, focus moves to the error summary.

Labelling

The title is the accessible name and the description sentence the accessible description, so both are announced on open. The icon is decorative. Name only one control “Close”; footer buttons name their outcome.

Motion

Backdrop fades in over --duration-base; the panel scales in (or slides up when full screen) over the same --duration-base with --ease-enter, the one overlay-entrance token (L2-089). Reduced motion shows both with no slide or fade.

Touch

On phones the footer sits at the bottom of the screen, within thumb reach, and respects the safe area. Buttons are 40px tall with 12px between; the close button is 40px square.

Content

  • Title: the decision as a question with the object named — “Delete “Maya’s 30th birthday”?”, “Reset invitation links?”, “Discard unpublished changes?” — or the task — “Edit guest”, “Add a block”.
  • Description: one sentence with the consequence or the rule: “This can’t be undone.”, “Your published page stays as it is.”
  • Buttons say what happens: “Delete event”, “Remove 2 guests”, “Send my regrets”. The safe action says what is kept when that is clearer than Cancel: “Keep editing”, “Keep my reply”.
  • Use the same noun in the trigger, title and button: “Schedule invitations” opens “Schedule invitations” and confirms with “Schedule invitations”.
