# L2 - Detailed Requirements

Conventions used in this file:
- Viewport bands: XS under 576px, SM 576px and up, MD 768px and up, LG 992px and up, XL 1200px and up.
- "Organiser" means a signed-in user who owns the event.
- "Guest" means an invitee using a personal link or invitation code. Guests are never signed in.
- Numeric limits are defined in the requirement that owns them. They are the system's contract and are covered by tests.

---

## L2-001: Organiser sign-in
**Traces to:** L1-001

An organiser must sign in with an email address and password. The sign-in form must show a loading state while the request is in flight and must block a second submission.

**Acceptance Criteria:**
1. Given a registered organiser, when they submit the correct email and password, then they are redirected to the dashboard and a session cookie is set with the HttpOnly, Secure and SameSite=Lax attributes.
2. Given an unknown email or a wrong password, when the organiser submits, then the page shows the same message "Email or password is not right" and does not reveal which field was wrong.
3. Given an empty or malformed email, when the organiser submits, then the form shows a field error on Email without sending a request.
4. Given a request is in flight, when the organiser presses Sign in again, then the button is disabled and no second request is sent.
5. Given "Keep me signed in" is ticked, when the session is created, then the session lifetime is 30 days; otherwise it is ended when the browser session ends.

---

## L2-003: Request a password reset
**Traces to:** L1-001

An organiser who has forgotten their password must be able to request a reset link without the system revealing whether the email is registered.

**Acceptance Criteria:**
1. Given any email address, when the organiser submits it on Forgot password, then the page shows "If that email is registered, a reset link is on its way." regardless of whether the account exists.
2. Given a registered email, when a reset is requested, then an email containing a single-use link is sent that expires after 60 minutes.
3. Given an empty or malformed email, when the organiser submits, then a field error is shown and no request is sent.

---

## L2-004: Reset password with a token
**Traces to:** L1-001

An organiser must set a new password from a reset link.

**Acceptance Criteria:**
1. Given a valid unused link, when the organiser enters a new password of at least 12 characters twice that match, then the password is changed, the link is marked used, all existing sessions for the account are ended, and the page shows success with a link to sign in.
2. Given an expired link, when it is opened, then the Reset password page shows the expired state with a button to request a new link.
3. Given a link that has already been used or is malformed, when it is opened, then the page shows the invalid state and no form.
4. Given a new password shorter than 12 characters or identical to the email address, when the form is submitted, then the field error explains the rule and the password is not changed.
5. Given the two password fields do not match, when the form is submitted, then the Confirm field shows "Passwords do not match" and no request is sent.

---

## L2-005: Session lifetime and sign-out
**Traces to:** L1-001

Sessions must end after inactivity and must be ended when the organiser signs out.

**Acceptance Criteria:**
1. Given a signed-in organiser who has been inactive for 8 hours, when they next make a request, then they are redirected to Sign in with the message "Your session ended. Sign in again."
2. Given a signed-in organiser, when they choose Sign out, then the server-side session is invalidated and the session cookie is cleared, so reusing the old cookie returns 401.
3. Given an active session, when the organiser's password is changed on another device, then that session is ended on its next request.

## L2-006: Create an event
**Traces to:** L1-002

An organiser must create an event from the New event page with the fields shown in the design: type, name, date, start time, venue (optional).

**Acceptance Criteria:**
1. Given valid name, type, date and start time, when the organiser selects Create event, then the event is created in Draft status and the organiser is taken to its Event overview page with a success toast.
2. Given Event name is empty or longer than 120 characters, when the form is submitted, then the field error is shown on Event name and nothing is saved.
3. Given a date in the past, when the form is submitted, then the field error "Pick a date in the future" is shown on Date.
4. Given a request is in flight, when the form is displayed, then Create event shows a busy state and Cancel remains available.
5. Given a server failure, when the request fails, then the form keeps every value the organiser entered and shows an error with a Try again button.

---

## L2-007: Event status
**Traces to:** L1-002

Each event must have one status derived from its data: Draft, Invites open or Invites closed.

**Acceptance Criteria:**
1. Given an event that has never been published, when its status is read, then it is Draft and its public page returns the not-open state for every guest.
2. Given a published event whose invite window has started and not ended, when its status is read, then it is Invites open.
3. Given a published event whose invite window has ended, when its status is read, then it is Invites closed.
4. Given an event's invite window changes, when the status is next read, then the new status is shown without a manual refresh of the list.

---

## L2-008: Edit event details
**Traces to:** L1-002

An organiser must edit the event details from Event settings.

**Acceptance Criteria:**
1. Given valid changes, when the organiser selects Save changes, then the changes are saved, the success toast "Changes saved" appears and the page shows the saved values.
2. Given an invalid value, when the form is submitted, then the field error is shown and the stored event is unchanged.
3. Given a save is in flight, when the form is displayed, then Save changes shows a busy state and the fields are read-only.
4. Given a save fails, when the error is shown, then the entered values are kept and the organiser can retry without re-entering them.
5. Given another user changed the event after this page was loaded, when the organiser saves, then the system shows "This event was changed elsewhere. Reload to see the latest version." and does not overwrite the change.

---

## L2-009: Invite window rules
**Traces to:** L1-002

Each event must have an invite window that opens and closes at specific times.

**Acceptance Criteria:**
1. Given the invite window close is before the open time, when the form is submitted, then the field error "Invites close after they open" is shown on Invites close.
2. Given the invite window closes after the event starts, when the form is submitted, then a warning is shown but the save is allowed.
3. Given the invite window is open, when a guest submits an RSVP, then the reply is accepted.
4. Given the invite window has closed, when a guest submits an RSVP or changes a reply, then the reply is rejected with the message "Replies closed on Sat 7 Nov, 11:59 pm" and nothing is changed.
5. Given the invite window has not opened, when a guest opens the public page, then the not-open state is shown with the open date.

---

## L2-010: Delete an event
**Traces to:** L1-002

Only the organiser must be able to delete an event. Deletion is permanent and must be confirmed.

**Acceptance Criteria:**
1. Given the organiser selects Delete event, when the confirm dialog opens, then it names the event, states that the page, invitees and responses will be removed and that this cannot be undone, and offers Cancel and Delete event.
2. Given the organiser confirms, when the delete succeeds, then the event, its guests, invitation links, scheduled emails and responses are removed and the organiser is returned to the events list with a toast.
3. Given the delete request fails, when the failure is shown, then the event and its data are unchanged and the dialog offers Try again.
4. Given the dialog is open with Delete event in progress, when the organiser presses Escape, then the dialog does not close until the request completes.

---

## L2-011: Regenerate invitation links
**Traces to:** L1-002

An organiser must be able to invalidate every invitation link and invitation code for an event, for example after a leak.

**Acceptance Criteria:**
1. Given the organiser selects Regenerate and confirms, when the request succeeds, then every previous personal link and invitation code for the event is rejected from that moment.
2. Given links were regenerated, when a guest opens an old link, then the Invitation link page shows the invalid state.
3. Given regeneration completes, when the page is shown, then it states that new links are sent with the next invitation email, and it does not show any link values.
4. Given regeneration fails, when the error is shown, then the old links continue to work.

---

## L2-012: Events list
**Traces to:** L1-002

The Events page must list all events the signed-in user can access and let them be found, filtered and sorted.

**Acceptance Criteria:**
1. Given 3 events, when the Events page loads, then each row shows name, type, date, invitees, reply summary and status, and the heading reads "3 events · 1 taking invites".
2. Given the list is loading, when the page renders, then row placeholders are shown and the page is not blank.
3. Given no events, when the page renders, then the empty state offers New event.
4. Given a search term with no matches, when it is applied, then the no-results state reads "No events match" with a Clear search action.
5. Given 500 events, when the list is displayed, then rows are paginated at 50 per page and sorting by Event date, Name or Recently updated changes the order without a full page reload.
6. Given the list request fails, when the error is shown, then the error state offers Try again and no rows are shown.

## L2-013: Add and reorder page blocks
**Traces to:** L1-003

An organiser must build the public page from blocks and reorder them without a mouse.

**Acceptance Criteria:**
1. Given the organiser selects Add a block, when the picker opens, then it lists Hero, Details, Schedule, Map, RSVP form, FAQ, Photo gallery and Gift list, each with a one-line description.
2. Given a block type is chosen and Add block is selected, when the block is added, then it is appended to the end of the page and is listed in the outline.
3. Given a block that is not first, when the organiser selects Move up, then it swaps position with the block above and focus stays on the moved block's Move up control.
4. Given the page has 12 blocks, when the organiser tries to add a 13th, then the picker shows "A page can have up to 12 blocks" and nothing is added.
5. Given a block is dragged, when the drag is complete, then the same order change is available via Move up and Move down, which are never removed.

## L2-014: Edit block content
**Traces to:** L1-003

Each block must have typed fields that are validated before it is saved to the draft.

**Acceptance Criteria:**
1. Given a Hero block, when the Headline is empty, then the field error "Add a headline" is shown and the draft is not saved with an empty headline.
2. Given a Headline longer than 120 characters or a Button label longer than 40 characters, when the field loses focus, then a counter shows the limit and the field error explains it.
3. Given a block is collapsed, when the organiser selects Expand, then its fields are shown with their values unchanged.
4. Given the organiser selects Remove block, when the block is removed, then it is removed from the outline and an Undo action is shown for 10 seconds.
5. Given an RSVP form block is added, when the page is published, then the form's fields match the RSVP fields in L2-040 and cannot be removed individually.

---

## L2-015: Draft and publish
**Traces to:** L1-003

Edits must be saved as a draft and only become visible to guests when published.

**Acceptance Criteria:**
1. Given the organiser edits a block, when 2 seconds pass without typing, then the draft is saved and the status reads "Draft · saved just now".
2. Given unpublished changes exist, when the organiser selects Publish, then the public page is updated and the status reads "Published · just now".
3. Given publish is in flight, when the organiser presses Publish again, then the second request is not sent.
4. Given publish fails, when the error is shown, then the draft is kept, the public page is unchanged and the organiser can retry.
5. Given a draft with validation errors, when Publish is selected, then publish is blocked and the first invalid field is focused.

---

## L2-016: Discard unpublished changes and leave guard
**Traces to:** L1-003

Organisers must not lose unpublished changes by accident.

**Acceptance Criteria:**
1. Given unpublished changes, when the organiser selects Discard changes, then the discard dialog asks "Discard unpublished changes?" with Keep editing and Discard.
2. Given the organiser confirms discard, when it completes, then the draft matches the last published version and the status reads "Published".
3. Given unpublished changes, when the organiser navigates to another page, then the browser warns before leaving with "You have unpublished changes".
4. Given discard fails, when the error is shown, then the draft is unchanged.

---

## L2-017: Preview the page as a guest
**Traces to:** L1-003

Organisers must see the page exactly as a guest will see it before publishing.

**Acceptance Criteria:**
1. Given unpublished changes, when the organiser selects Preview, then the preview renders the draft with the same components the guest page uses.
2. Given a preview is open, when a guest opens the public page at the same time, then the guest sees only the published version.
3. Given the preview is open, when the viewport is XS, then the preview fills the width with no horizontal scroll.

## L2-018: Photo gallery uploads
**Traces to:** L1-003

Photos in the gallery block must be limited and checked before they are stored.

**Acceptance Criteria:**
1. Given a gallery with 12 photos, when the organiser uploads another, then the upload is refused with "A gallery holds up to 12 photos".
2. Given a file that is not JPEG, PNG or WebP, or whose content does not match its extension, when it is uploaded, then it is rejected with "Use a JPEG, PNG or WebP photo".
3. Given a photo larger than 5 MB, when it is uploaded, then it is rejected with "Photos must be 5 MB or smaller".
4. Given a valid photo, when it is stored, then location and camera metadata are removed and the image is re-encoded.

## L2-019: Guest list table
**Traces to:** L1-004

The Guests page must show every invitee with their key details.

**Acceptance Criteria:**
1. Given 6 guests, when the Guests page loads, then each row shows name, email, group, reply, party size, last updated and Edit and Remove actions.
2. Given 2,000 guests, when the page loads, then 50 rows are shown per page with pagination controls and the total count "2,000 invitees".
3. Given the list is loading, when the page renders, then placeholder rows are shown.
4. Given the list request fails, when the error is shown, then "We couldn't load your guests. Nothing was changed." appears with Try again.
5. Given no guests, when the page renders, then the empty state offers Add guest and Import CSV.

## L2-020: Search and filter guests
**Traces to:** L1-004

Organisers must find guests quickly.

**Acceptance Criteria:**
1. Given the search field, when the organiser types "lisbon" and pauses for 300 ms, then the list shows only guests whose name or email contains that text, case-insensitively.
2. Given the filter is set to Waiting, Attending or Declined, when applied, then only guests with that reply status are listed and the chip shows the active filter.
3. Given no matches, when the search is applied, then the no-results state reads "No guests match 'Lisbon'" and offers Clear search.
4. Given a search or filter is active, when the organiser selects Clear search, then the full list and the All filter are restored.

## L2-021: Add a guest
**Traces to:** L1-004

Organisers must add a guest one at a time from the Add guest dialog.

**Acceptance Criteria:**
1. Given Full name and a valid email, when the organiser selects Add guest, then the guest is added with status Waiting and the dialog closes with a toast.
2. Given an email that is malformed, when the dialog is submitted, then the field error "Enter an email like name@example.com" is shown and no guest is added.

4. Given Full name is empty or longer than 120 characters, when the dialog is submitted, then the field error is shown on Full name.
5. Given the Plus-ones field, when a value is entered, then it accepts whole numbers from 0 to 9 only, with 0 as the default.
6. Given the add request fails, when the error is shown, then the dialog keeps the values and offers Try again.

Organisers must edit a guest's details, group and number of places.

**Acceptance Criteria:**

## L2-024: Select guests
**Traces to:** L1-004

Organisers must select guests to act on several at once.

**Acceptance Criteria:**

2. Given some rows are selected, when the header checkbox is selected, then it is shown in an indeterminate state and selects the current page only.

## L2-025: CSV import upload and validation
**Traces to:** L1-004

A guest list can be imported from a spreadsheet, but nothing is saved until the file has been checked.

**Acceptance Criteria:**
1. Given a file that is not a .csv, when it is chosen, then it is rejected with "Choose a .csv file".
2. Given a file larger than 5 MB or with more than 2,000 data rows, when it is chosen, then it is rejected with the limit that was exceeded.
3. Given a valid file, when it is chosen, then the Map columns step lists each detected column and its target field.
4. Given a file with no Email column, when it is parsed, then the error "Email is needed to send invitations" is shown and the import cannot continue.
5. Given the file is not valid UTF-8, when it is parsed, then the error "The file must be saved as UTF-8" is shown.

## L2-026: CSV import mapping, review and commit
**Traces to:** L1-004

Each row must be checked and the organiser must confirm before guests are created.

**Acceptance Criteria:**
1. Given the Review step, when rows have errors, then each error row is listed with its row number and the reason, and Import is disabled until the errors are fixed or the rows are skipped.
2. Given a row whose email already exists in the event, when the import is reviewed, then the row is marked Duplicate and is skipped, and the summary states how many were skipped.
3. Given the organiser confirms the import, when it completes, then the Done step shows the number imported, skipped and failed, and a link to the Guests page.
4. Given the import is interrupted by a network failure, when the organiser retries, then no guest is created twice.
5. Given a row has a group that is not Friends, Family or Work, when it is reviewed, then it is shown as "Group will be set to Friends" and the import continues only after the organiser accepts it.

## L2-029: Schedule invitations
**Traces to:** L1-005

Organisers must schedule the invitation email for all invitees or only for those who have not replied.

**Acceptance Criteria:**
1. Given the Schedule invitations dialog, when it opens, then Recipients offers All invitees (with the count) and Only people who haven't replied, and Send on defaults to the invite window open date.
2. Given the Subject is empty or longer than 150 characters, when the dialog is submitted, then the field error is shown and nothing is scheduled.

5. Given scheduling fails, when the error is shown, then the dialog offers Try again and no partial schedule is recorded.
6. Given scheduling is in flight, when the dialog is displayed, then Schedule invitation shows a busy state and fields are read-only.

## L2-032: Reminder audience and cancellation on reply
**Traces to:** L1-005

Reminders must reach only guests who have not replied, and a reply must stop reminders for that guest.

**Acceptance Criteria:**
1. Given a reminder scheduled for "Invitees who haven't replied", when it is sent, then only guests with status Waiting at send time receive it.
2. Given a guest with a pending reminder, when that guest replies yes or no, then the pending reminder for that guest is cancelled and not sent.
3. Given a reminder scheduled after the invite window closes, when the schedule is saved, then it is refused with "Reminders must go out before invites close".

## L2-033: Personal invitation links
**Traces to:** L1-005

Each guest must have a personal link that identifies them without sign-in.

**Acceptance Criteria:**
1. Given a guest is added to an event, when their invitation is first sent, then a link is generated containing a random token of at least 128 bits.
2. Given a link is opened, when the token matches a guest in an open or not-yet-open event, then the invitation page is shown for that guest.
3. Given the same guest is sent a reminder, when the reminder is sent, then the link in the reminder is the same link as the invitation.

---

## L2-034: Delivery outcomes and bounces
**Traces to:** L1-005

Organisers must know which emails did not arrive.

**Acceptance Criteria:**
1. Given the email provider reports a permanent bounce for a guest, when the event is viewed, then the guest is flagged "Email bounced" in the guest list and an in-app notification is created.
2. Given a bounced guest, when reminders are scheduled, then that guest is excluded from the reminder and the Recipients count reflects the exclusion.
3. Given a bounce is reported after the guest has been emailed successfully before, when it is processed, then the guest's most recent status is shown.

---

## L2-035: Reliable and idempotent sending
**Traces to:** L1-005

Emails must be sent once even when the system retries.

**Acceptance Criteria:**
1. Given a send times out after the provider accepted it, when the job is retried, then the provider receives the same idempotency key and the guest receives one email.
2. Given a temporary provider error, when the send fails, then it is retried with exponential back-off up to 5 times over at most 1 hour before it is marked Failed.
3. Given an email is marked Failed, when the Emails page is viewed, then the row shows Failed with a Retry action.

---

## L2-036: Sender identity and reply-to
**Traces to:** L1-005

Emails must come from the organiser's name and replies must reach the organiser.

**Acceptance Criteria:**

2. Given an invalid reply-to address, when the settings are saved, then the field error "Enter a valid email address" is shown and the setting is unchanged.
3. Given the sender name contains line breaks, when it is saved, then the line breaks are removed before use.

## L2-038: Personal link access and invalid links
**Traces to:** L1-006

Personal links must open the correct invitation and fail safely otherwise.

## L2-040: RSVP form fields
**Traces to:** L1-006

The RSVP form must collect the fields shown in the design, with conditional fields appearing only when relevant.

## L2-042: RSVP submission
**Traces to:** L1-006

A valid reply must be stored once and confirmed to the guest.

**Acceptance Criteria:**
